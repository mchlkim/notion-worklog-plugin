# Notion Worklog Skill

어떤 에이전트가 작업하든 **같은 Notion 보드**에 계획 → 실행 → 결과를 남긴다.
나중에 사람이나 다른 에이전트가 "그때 왜 그렇게 했지"를 추적할 수 있게 하는 것이 목적이다.

## 언제 쓰나

**기록한다**
- 파일·인프라를 실제로 변경하는 작업
- 여러 단계에 걸치거나 한 세션에 안 끝날 작업
- 조사/분석처럼 결론이 산출물인 작업
- 사용자가 과거 이력을 물을 때 (이때는 조회만)

**기록하지 않는다**
- 단순 질문 답변, 한 줄 조회, 읽기 전용 탐색
- 사용자가 명시적으로 "기록하지 마"라고 한 경우

## 기록 대상 찾기

1. 환경변수 `NOTION_WORKLOG_DATA_SOURCE_ID` 가 있으면 그 값을 쓴다.
2. 없으면 `assets/worklog.config.json` 의 `notion.dataSourceId` 를 읽는다.
3. 둘 다 없거나 접근이 안 되면 `references/bootstrap.md` 를 따라 DB를 새로 만들고,
   만든 ID를 `assets/worklog.config.json` 에 써 넣는다.

**프로젝트 노트 DB**(아래 절 참조)는 `NOTION_WORKLOG_PROJECT_NOTES_ID` →
`notion.projectNotesDataSourceId` 순서로 같은 방식으로 찾는다.

## 필요한 도구

Notion MCP 서버(`https://mcp.notion.com/mcp`)의 도구를 쓴다.
**클라이언트마다 도구 이름 접두어가 다르므로** 이름 끝부분으로 찾을 것:

| 하는 일 | 도구 (접두어 제외) |
|---|---|
| 스키마·기존 카드 확인 | `notion-fetch`, `notion-search` |
| 카드 생성 | `notion-create-pages` |
| 카드 수정 | `notion-update-page` |

예: Claude Code는 `mcp__claude_ai_Notion__notion-create-pages`, 다른 클라이언트는 `notion.create_pages` 형태일 수 있다.

> Notion MCP를 못 찾으면 **조용히 넘어가지 말고** 사용자에게 알린다:
> "Notion MCP가 연결돼 있지 않아 작업 기록을 남기지 못합니다. `https://mcp.notion.com/mcp` 를 연결해 주세요."

## 절차

### 1) 착수 — 카드 생성

`notion-create-pages` 로 `data_source_id` 를 부모로 하는 페이지를 만든다.

- `작업명`: **한 줄 요약만.** `[프로젝트]` 같은 대괄호 접두어를 붙이지 않는다 —
  분류는 `프로젝트` 속성이 담당하므로 제목에서 중복시키면 보드가 지저분해진다.
  예: `API 서버 v2 마이그레이션` (`[프로젝트A] API 서버 v2 마이그레이션` 아님)
- `상태`: `계획`
- `에이전트` / `모델`: 지금 돌고 있는 에이전트와 모델명
- `프로젝트`(select): 이 작업이 속한 고객사·프로젝트. **분류·필터의 유일한 키**다.
  **데이터소스를 먼저 조회해 기존 옵션 중에서 고른다.** 맞는 옵션이 없으면
  임의로 만들지 말고 사용자에게 어느 프로젝트인지 묻는다. 규칙 전문은
  [references/schema.md](references/schema.md).
- `유형` `우선순위` `시작` `작업경로` 채움.
  `작업경로` 는 git 최상위(`git rev-parse --show-toplevel`), 아니면 cwd의 절대경로.
- `세션ID`: **`scripts/session-id.sh` 를 실행해 채운다.**
  종료코드가 0이면 그 출력값을 넣고, 1이면 **비워 둔다** (추측한 값을 넣지 않는다).
  Claude Code는 `CLAUDE_CODE_SESSION_ID` 환경변수를, Codex는 최신 롤아웃 파일명을 쓴다.
- `관련 작업`(relation): 이 작업의 선행 카드·이어서 하는 카드가 있으면 연결한다.
  값은 카드 페이지 URL 배열이다. 없으면 비워 둔다.
- 본문: `assets/card-template.md` 의 `1. 계획` 과 `7. 하네스` 섹션을 채워서 넣는다.
  **`7. 하네스` 는 본문 맨 끝** — 이 작업에 쓰는 스킬·MCP 서버(도구 이름까지)·CLI·
  서브에이전트를 남긴다. 항목은 다른 섹션처럼 **제목2**(`## 스킬`)로 두고 내용은
  다음 줄에 쓴다. 작업 중 새 도구를 쓰게 되면 그때 덧붙인다.
  **`목표: 내용` 처럼 한 줄에 붙이지 않는다** — `## 목표` 를 제목2로 두고 다음 줄부터
  일반 텍스트로 쓴다. 본문 작성 규칙은 아래 절을 따른다.

카드 URL을 기억해 뒀다가 이후 수정에 쓴다. 사용자에게 URL을 한 줄로 알린다.

### 2) 진행 — 상태만 옮기고 로그는 append

착수하면 `상태` = `진행중`.

의미 있는 결정과 시행착오가 생길 때만 본문 `2. 실행` 에 **덧붙인다**.
`notion-update-page` 의 `update_content` (search/replace) 를 써서 해당 섹션에만 추가한다.
`replace_content` 로 본문 전체를 다시 쓰지 말 것 — 이전 기록이 날아간다.

기록 가치가 있는 것: 방향을 바꾼 판단, 막혔던 지점과 원인, 버린 대안과 이유.
기록하지 말 것: 명령어 나열, 성공한 단순 반복 작업.

### 3) 종료 — 결과 채우고 `검증` 으로

`결과`(`성공`/`부분성공`/`실패`/`롤백`) · `완료일` · `브랜치/커밋` · `푸시` 를 채우고
본문 `3. 결과` · `4. 개선점` · `5. 출처` · `6. 산출물` 을 작성한 뒤 `상태` = `검증`.

`3. 결과` 의 "남은 일"이 비어 있지 않으면 **`미해결` 을 체크**한다. Home 의
"미해결 남은 카드" view 와 lint 가 이 체크를 보고 후속 작업을 챙긴다.

마지막으로 **프로젝트 노트를 환류**한다: 프로젝트 노트 DB에서 이 카드의 `프로젝트` 와
같은 제목의 페이지를 찾아(없으면 생성) `4. 개선점` 의 새 항목을 "누적 개선점"에,
남은 질문을 "미해결 질문"에 덧붙이고 "현재 상태"가 낡았으면 고쳐 쓴다.
카드 본문과 마찬가지로 **append 원칙** — 노트 전체를 다시 쓰지 않는다.

`5. 출처` 는 참고한 문서·스펙을 제목과 URL로 남긴다. 추측으로 판단한 부분은 출처가 없다고 적는다.
`6. 산출물` 은 생성·변경한 파일 경로와 PR·커밋·리소스를 나열한다.

`브랜치/커밋` 은 **`브랜치@짧은해시` 를 커밋 URL로 하이퍼링크**한다.
텍스트 속성이 마크다운을 해석하므로 `[main@0e89e71](<원격URL>/commit/<전체해시>)` 로 쓴다.
원격이 없으면 링크 없이 `main@0e89e71`, git 레포가 아니면 비워 둔다.

**이 속성에는 `브랜치@짧은해시` 외에 아무것도 쓰지 않는다.** `(pushed)` · `(미커밋)` ·
`git 미추적` 같은 부연을 붙이지 말 것 — 커밋이 없으면 그냥 비워 두면 되고,
푸시 여부는 바로 옆 `푸시` 체크박스가 담당한다.

`푸시` 는 **`git branch -r --contains <해시>` 의 출력이 비어 있지 않으면 체크**한다.
원격이 없거나 커밋이 없으면 체크하지 않는다. 방금 커밋만 하고 푸시하지 않았다면
체크하지 않은 채로 두고, 나중에 푸시하면 그때 체크한다.

**`완료` 로 옮기는 것은 사람이 확인한 뒤**다. 에이전트가 스스로 `완료` 로 올리지 않는다.
사용자가 확인했다고 하면 `상태` = `완료` 로 옮긴다.

### 4) 실패해도 카드를 남긴다

`상태` = `중단/실패`, `결과` = `실패` 또는 `롤백`, 사유를 본문에 적는다.
실패 기록이 다음 작업에 더 유용하다. 카드를 지우지 않는다.

## 본문 작성 형식

**섹션은 제목1(`#`), 그 안의 항목은 제목2(`##`), 내용은 그 다음 줄에 일반 텍스트.**

```markdown
# 1. 계획

## 목표
사내 API 게이트웨이를 v2 스키마로 옮긴다.

## 범위 / 범위 밖
게이트웨이와 인증 미들웨어까지. 클라이언트 SDK는 이번에 건드리지 않는다.
```

`- 목표: 사내 API 게이트웨이를 ...` 처럼 라벨과 내용을 한 줄에 붙이지 않는다.
Notion에서 접기·링크·목차가 헤딩 단위로 동작하므로, 항목이 헤딩이어야 나중에 찾아 읽기 쉽다.

항목이 **이름 붙은 칸**이면 제목2를 쓴다 — `목표`, `범위 / 범위 밖`, `접근 방법`,
`리스크 & 롤백 방안`, `검증 방법과 결과`, `남은 일 / 후속 조치`,
그리고 `7. 하네스` 의 `스킬` · `MCP` · `CLI / 도구` · `서브에이전트`.

항목이 **목록**이면 헤딩으로 쪼개지 않고 불릿을 유지한다 — `2. 실행` 의 시간순 로그,
`4. 개선점`, `5. 출처`, `6. 산출물`. 개수가 정해져 있지 않고 계속 덧붙는 것들이다.

**파일명·경로는 백틱으로 감싼다.** 맨 텍스트로 `schema.md` 를 쓰면 Notion이 도메인으로 보고
`[schema.md](http://schema.md)` 로 자동 링크해 버린다. `` `schema.md` `` 처럼 인라인 코드로 쓰면
그대로 남는다. `6. 산출물` 의 파일 목록에서 특히 자주 걸린다.

## 프로젝트 노트 — 카드가 쌓이면 종합한다

카드는 **append-only 로그**고, `프로젝트 노트` DB는 그 위에 유지되는 **종합 계층**이다.
프로젝트당 페이지 하나. 본문은 네 섹션 — `# 현재 상태` / `# 누적 개선점` /
`# 미해결 질문` / `# 변경 이력`.

- 착수 때 읽고, 종료 때 환류한다 (위 절차 참조).
- 카드와 달리 **유지·갱신되는 문서**다. 다만 갱신은 섹션 단위로 하고,
  기존 항목을 지울 때는 이유를 `# 변경 이력` 에 남긴다.
- 환류할 때 이미 있는 항목과 같은 내용이면 중복 추가하지 않는다. 같은 지적이
  반복되는 것이면 항목 뒤에 횟수를 표시한다 (예: `(3회째 — 작업화 제안됨)`).

## 조회 결과도 환류한다

사용자가 과거 이력을 물어 정리해 준 결과(프로젝트 요약, 기간별 작업 정리, 비교 등)가
**재사용 가치가 있으면** 프로젝트 노트에 반영하자고 사용자에게 제안한다.
좋은 정리가 채팅 로그에서 증발하는 것을 막는 게 목적이다.
단발성 확인("어제 뭐 했지" 수준)은 환류하지 않는다.

## 중단된 작업 이어받기

카드의 `resume` 속성이 `cd <작업경로> && claude --resume <세션ID>` 형태의 명령을 자동으로 만든다
(`세션ID` 와 `에이전트` 에서 계산되므로 채워 넣지 않는다).

사용자가 지난 작업을 이어가고 싶어 하면 `scripts/resume.sh <세션ID>` 를 실행해 명령을 만들어 준다.
`작업경로` 속성이 비었거나 낡았어도 트랜스크립트에 기록된 실제 cwd 를 찾아 쓴다.

**에이전트가 직접 실행하지 않는다.** 현재 세션 안에서 중첩 대화형 세션이 떠 그대로 멈춘다.
명령만 보여주고 사용자가 실행하게 한다.

## 규칙

- **작업 단위로 카드를 나눈다.** 한 대화에서 세 가지 일을 했으면 카드도 세 개다.
- **제목에 대괄호 접두어를 쓰지 않는다.** `[EDP] 월간보고서 수정` 이 아니라
  `월간보고서 수정` + `프로젝트` = `EDP`.
- 이미 진행 중인 카드가 있는지 먼저 확인한다 (`notion-search` 또는 `상태` 필터). 같은 작업을 중복 생성하지 않는다.
- 착수 전에 **프로젝트 노트에서 해당 프로젝트 페이지를 먼저 읽는다.** 카드를 일일이
  뒤지는 것보다 종합본 한 장이 빠르다. 노트가 없으면 같은 `프로젝트`·`작업경로` 의
  지난 카드 `4. 개선점` 을 읽고, 종료 시 노트를 만들어 환류한다.
  같은 지적이 세 번째 나오면 그것 자체를 작업으로 만들자고 사용자에게 제안한다.
  같은 경로의 카드가 쓰던 `프로젝트` 값이 있으면 그대로 재사용한다.
- 속성 값은 **정해진 옵션 안에서만** 쓴다. 새 값이 필요하면 사용자에게 확인하고 옵션을 추가한다.
  `프로젝트` 도 예외가 아니다 — 고객사·프로젝트 이름은 사람이 정하는 값이라 추측해서 만들지 않는다.
- 고객 데이터, 자격증명, 내부 IP·계정 정보는 본문에 쓰지 않는다. 경로와 리소스명 수준까지만.
